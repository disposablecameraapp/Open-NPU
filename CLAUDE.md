# Open NPU: notes for Claude

Windows on Snapdragon (ARM64) desktop app: Electron main process in `src/main`, React renderer in `src/renderer`, logic shared by both in `src/core`, tests in `tests`. The user writes in French; answer in French.

## Rules that were broken before. Do not break them again.

1. **Hooks go above every early `return` of a component.** A `useState`, `useEffect`, `useMemo`, `useRef`... placed after `if (!x) return ...` makes React throw error #310 ("Rendered more hooks than during the previous render") and the window shows "Open NPU hit a problem drawing the window". It happened in `Chat.tsx`, which returns early when no model is selected, and it happened more than once. `tests/hooks.test.ts` reads every renderer component and fails on a hook after an early return: run it. When adding state to a component, read the whole function first and put the hook with the other hooks, at the top.
2. **Pull requests target `main`, never another `claude/...` branch.** Work merged into an intermediate branch never reached `main` before. When creating a PR, check the base. Before saying something is done, check that it is in `main`.
3. **Before pushing:** `npm ci` (if `node_modules` is missing), `npx tsc --noEmit -p tsconfig.main.json`, `npx tsc --noEmit -p tsconfig.renderer.json`, `npx vitest run`. All must pass. A push to `main` builds the Windows installer in CI (`.github/workflows/release.yml`) and publishes `Open-NPU-Setup.exe` on the `latest` release; that build runs the tests on Windows, where timing-based tests can differ. `git pull --no-rebase` first: other sessions push to `main` too.
4. **No model name or tool name in commit messages or code comments.** Commits end with the attribution lines given by the session.

## What the user wants (decided, do not reopen)

- Models should run **on the NPU**. Badges on every model: NPU (best), Hybrid (part on the CPU), CPU (worst). Hybrid and CPU are never chosen silently: they are a last resort the user allows (`allowHybridLoad`), and the badge says it.
- A model the app does not know (not in the catalog, not in a Dynamic pack) is **checked once after it is installed**: loaded under the best setting this PC accepts, NPU first, then badged. Only loading is checked, never the quality: how good a model is stays the user's call.
- When the app sees the NPU is stuck it **resets it by itself** (scheduled task created once with one Windows permission, then no prompt). Do not make the user press a button or restart the PC.
- The benchmark has a **Launch check** mode (does each model load and answer, no quality tests) and Developer settings has a page that compares GenieX with Microsoft Foundry Local on the same models (`src/core/foundry.ts`, `src/renderer/EngineCompare.tsx`). The Foundry Local side is written from its documentation, not tried against a real install.
- **Building files (`src/core/build.ts`):** a program (game, tool, any size) is ONE page, and **every program is built by the construction engine, whatever the length of the request: a short request ("make tetris") is not a reason for a lighter way, that gave poor games (decided, do not bring back the "small request = no plan" shortcut).** What the person wants is decided by closed yes/no questions put to a model (the router, else the chat model), never by the length of a message or word lists (the words only stand in when no model answers). Ready-made starting pages (`skeletons.ts`) and the arcade JSON engine are used only when the person asks outright ("from scratch" / code brut gives one session writing the code, "with the engine" gives the engine). A file is never cut into pieces written apart: a file too long for the window is continued by the same session. The contract shared between files is read from the code, not from a model, and checked (a page's own script must parse and find its elements). The user sees which file is being worked on, its code and preview live, and a line saying what happens now: every file shows its stages (starting point, rules, write, check, fix) as chips with their time, **the Code tab of a page made by the construction engine has a picker (`code-pick` in `ArtifactView.tsx`): "Writing now · name" follows the unit being written as it comes (`BuildRun.unit`, set by `unitAsk` in `build.ts`), "Whole file", or any one unit read from the page's `/* unit:name */` marks; when the work ends it goes back to the whole file**, and the finished page gets a visible test run (it is run, its keys and buttons pressed, a screenshot shown) with a fix and a second run when it shows a problem; a fix that makes it worse is undone. The tested pages of `src/core/skeletons.ts` are no longer a starting point unless the person asks for one; short written rules first only happen on the "from scratch" way, for a program that is not a game. Helper sessions that mend a file think (medium effort), those that write do not. In the browser preview (`npm run dev:renderer`) a message with "snake" plays this whole pipeline with a pretend model. Speak as one assistant ("I", never "we"): the files are the assistant's own work, never "the code you gave me".
- **Foundry Local models are part of the app** (Models, "Microsoft Foundry Local", `foundryCatalogEntries` in `src/core/foundry.ts`): listed from `foundry model list` (which does not start its daemon), installed with `foundry model download`, run through its server for the chat, badged NPU / Hybrid / GPU / CPU by the hardware of their build until measured, and the person can mark any of them differently (`setRunsOn`). They are not in `allEntries()` on purpose (that list is what the benchmark tests with GenieX); look a model up with `entryById`.
- **The Dynamic model uses the best build whatever the engine.** The app is called Open NPU: when Foundry Local has a build of a pack model made for the NPU that measured faster, the pack runs that one (`foundry` on the model in `dynamic-data.json`, installed with Foundry Local, which is installed too for a model only it has, `foundryOnly`); the GenieX file is the way out when Foundry Local is not there or fails. Starting a server is never a reason to keep a slower build. When two engines were tested on the same model, the faster one is shown and used: the quality of a short test varies, so it does not decide.
- **One engine and no leftovers.** Whatever starts a model first closes the servers that are not this app's (`closeStrayServers`: a geniex whose parent is not this app, Foundry's daemon when no Foundry model is in use) before the heavy NPU reset. The app's own server and its conversations are left alone. Foundry's daemon is stopped after each Foundry model: it keeps RAM, and the NPU works in RAM.
- **Foundry Local facts measured here:** its NPU builds size the attention cache on prompt + `max_tokens` and run the prompt in blocks of 64, so a small `max_tokens` (12, 16) kills its daemon (`GroupQueryAttention` errors): ask for at least 256. Its server refuses non-zero penalties (`presence_penalty`): a request refused for an optional field is sent again without it (`streamChat`). The model is asked by the build id it announces when loaded, not by its alias.
- **The Dynamic model has a router** (`src/core/router.ts`, `RouterPanel.tsx`): a tiny model (Qwen3-0.6B, about 0.4 GB) that reads the requests the words are unsure about and names their kind in one word, a second or so. It runs on the PROCESSOR, in a second `geniex serve --compute cpu` on port 18182 (`routerSrv` in `main.ts`), never on the NPU (which holds one model, and swapping it for every request would cost more than the answer). This is decided: the user wanted a "System 1" model and said to build it, so the rule against silent CPU use does not apply to it. It needs no training (the kinds and examples are in its prompt), has a short timeout and always falls back to the words' guess, and is installed from the Dynamic settings. Its answer is shown in the chat ("sorted by the router").
- **Recommended means fully on the NPU, from any provider.** The Recommended list and Dynamic never use a model known to run hybrid, on the GPU or on the CPU (`recommendedModels`, `onNpuOnly` in `main.ts`); when a model exists on two engines, the full-NPU build is the one shown, then the faster. Foundry Local is one provider among others (GenieX GGUF, native bundles), never the criterion. Dynamic falls back to a non-NPU model only when nothing else of the pack is installed.
- **The router belongs to the packs** (`router` of each pack in `dynamic-data.json`, outside `models` so it is never picked to answer): installing or removing a pack installs or removes it (`packParts`).
- **Tested models are written in the app** (`src/core/tested.ts` for the list, `scores.json` for speed, quality, where they ran and, when it was not the usual one, the load setting they needed): they are listed with their measures installed or not (Foundry Local ones too, when Foundry Local is not there; installing one installs it first), and the ones that did not run fully on the NPU sit in the folded "Not fully on the NPU" section, never recommended. A new benchmark result is added to these two files.
- **Drawn blocks, no code (`src/core/visualRoute.ts`, `chart.ts`, `diagram.ts`, `blocks.ts`; `ChartBlock`, `DiagramBlock`, `Figures`, `Tex` in the renderer).** A chart, graph, diagram, calculator with inputs, QCM, checklist or spreadsheet is NOT a web page: the model writes a fenced block and the app draws it (`chart` with sliders, exact number fields, `formulas` typeset by KaTeX with the person's values, `outputs` cards and an axis that follows a param; `mermaid` for flows, sequences, org charts, mind maps, timelines, Gantt, states, classes, ER; `kpi`, `quiz`, `cards`, `checklist`, `sheet` that recalculates, markdown tables, `$..$` formulas). `routeVisual` decides from the words, with no model call, and a routed request skips the planner and gets only the rules of its picture. **It never forces:** a request for a document (report, course, fiche, guide...) is a markdown artifact with the blocks inside, and with files in the chat a request is a change to them (the build steps decide). Writers and editors of a `.md` file are given the block rules (`docNote`). A quiz or checklist as a block is decided; a quiz *game*, a keypad calculator, a stopwatch or a to-do app still start from `skeletons.ts`. Mermaid is loaded on first use (dynamic import) and KaTeX/Mermaid are devDependencies because vite bundles them. **Everything drawn is corrected automatically when it could fail:** charts (`settleCharts`) and quiz/sheet/kpi/cards/checklist blocks (`blockFlaw`, `settleBlocks`) are checked in `main.ts` once the answer is done and given back to the model with the reason; a diagram is healed in the window (`healDiagram`: safe repairs, then the model through `fixBlock` twice, then the offending line is left out) because only the window can draw Mermaid. A new block needs a `blockFlaw` case. When adding a block: parser in `core`, a test in `tests/visuals.test.ts`, its rules in `BLOCK_INSTRUCTIONS` and a case in `Markdown.tsx`.
- **Office documents: Word, Excel, PowerPoint (`src/core/office.ts`, `officeRead.ts`, `slides.ts`, `deckBuild.ts`, `sheet.ts`, `figures.ts`, `zip.ts`, `xml.ts`; `ArtifactEditor`, `figureImages.ts`, `docs.ts` in the renderer; `convert.ts` in main).** No dependency: a zip and an XML reader of our own, validated against python-docx/pptx, openpyxl and LibreOffice. The model never writes XML: an artifact of type `docx` (markdown), `xlsx` (`## Sheet` then a `| table |`, first line = row 1, first column = A, `=formulas` that the app calculates, `AVG` and European numbers accepted) or `pptx` (slides split by `---`, `Theme:`, `Chart:` above a table, `Flow:`, `![c](wikimedia:File)`, a fenced `mermaid` or `chart` block, `Notes:`) holds the text form, the app turns it into the real file on Save as, and the usual `<edit>` blocks change it (the old edit system applies as is). A real file is turned into the same text: attachments, project knowledge and the project folder (`documentText`: also OpenDocument and RTF; old `.doc/.xls/.ppt` go through LibreOffice when it is installed, `convertLegacy`, else the person is told to save a newer format). The text of an Excel file lists the calculated result of every formula. **The slide layout is ONE function (`layoutSlide`) drawn twice**, as the real .pptx and as the HTML preview, so the screenshot checked is what the file holds; charts (bar, line, pie), flows and tables are native shapes, a picture is cropped to fill and a figure is shown whole. **The drawn blocks of `blocks.ts` / `chart.ts` / `diagram.ts` are compatible:** in a docx, `kpi`, `cards`, `quiz`, `checklist`, `sheet` become tables and lists (`blockToMarkdown`) and `mermaid` / `chart` become pictures; in a pptx a `mermaid` or `chart` block becomes a picture; only the window can draw those, so the renderer makes the PNG (`figureImages.ts`, light colours) and passes it with the export (`exportArtifact(id, images)`) or on request while a deck is made (`figure` events, `requestFigure` in main). A `sheet` block has a "Save as .xlsx" button. **A presentation made from nothing goes through its own steps (`makeDeck`, before the planner of `stepwise`):** plan (theme from six, slide list, a visual per slide), the text of each slide within fixed limits (`LIMITS`; checked, one retry, then `trimSlide`), the visuals (Wikimedia pictures when the Pictures tool is on, diagrams, charts only from numbers the user gave), then a screenshot of each slide (`renderSlide` in `runcheck.ts`: text cut off, picture not loaded, plus a viewer model when one is installed), a fix that is undone if it makes the slide worse. Its progress is a `BuildRun` with one step per slide. A change to a deck that exists is NOT this pipeline: it goes the usual way with edit blocks. The person can edit an artifact's text by hand (Edit tab, `ArtifactEditor`, only when no answer is being written); the edit rewrites the answer's text so the model reads the new version. Charts of the deck pipeline are only drawn from data in the request: never invent numbers.
- **The journal of the work (`src/core/workLog.ts`, `WorkLog.tsx`, `BuildProgress.tsx`).** Whatever the task, progress is a short list of steps read from the top down: the two last finished (fading), the one running, the next one, and one quiet line ("3 done · 2 to come") that opens the whole list; finished work folds to one line ("6 steps · 1m 04s", a tick). Under the title a sentence of the step renews itself every few seconds (`phrasesFor`, sober, no jokes, no typewriter); the real detail of the moment sits on the running row. The road map (rail) shows every file and the test run from the start, dashed until they begin. The journal is for complex work only (`deriveWork`): a build of files, a document (its sections are its steps), several helpers, searches and helpers that add up to three, an improve loop. A question, a single search or a model loading never get it: they keep their search card, the line of their thinking and the Presence line, and only small animations are added to those. Writing the answer is never a step. The block never changes height while it runs (the list reserves four rows, the strip under it a fixed height); finished, it folds to one small quiet line. Rejected on purpose, do not bring back: a chip of lit cells, a metro line, a hive of agents, a pulse trace, a minimap, round avatars, a glowing border, a feed that adds new items at the top. Nothing childish. **Steps are marked by their own drawing** (`StepIcon.tsx`, one per kind of step, moving in the accent colour while it runs, grey and still when done, faint while it waits): never a tick or an empty circle. **Simple tasks** (sorted by the router, a file read, thinking, searches, project files; `deriveSimple`, `ActivityGroup`) show only the LAST step as a line with its drawing, two lines while it works (title and a sentence that changes, the thought glides line by line), one quiet line when finished, with the other steps and their cards one click away. The model loading is one line with a sliding segment, never a made-up percentage (`LoadingLine`).
- **Arcade games are described, not programmed (`src/core/engine.ts`).** Like a chart or a diagram: the model fills a JSON description (things, rules) that follows `GAME_SCHEMA` (sent to the server as `response_format`, dropped by `streamChat` if refused) and a runtime of our own (`ENGINE_SOURCE`: loop, keys, mouse, movement, collisions, score, lives, restart) plays it. Since the construction engine builds every program, this engine and the hand-written way are chosen only when the person says so outright (`explicitWay`: code brut / from scratch / sans librairie, or "with the engine"); the old default (the engine for a classic arcade game, `chooseGameWay`) is no longer used. A description that fails `gameFlaw` twice falls back to the usual writer. The page (`gamePage`) keeps the description readable, so a change is an edit of a few lines. Save as offers the page, plain code (`.js`, engine and game in one file) or the description (`.json`) (`exportGame`, `specOfPage`). Skeletons are untouched for now (snake and the like still start from them).
- **Games with a world and small apps are pages of blocks (`src/core/xblocks/*.js`, `xdocs.ts`, `xplan.ts`, `xbuild.ts`, `xcheck.ts`, `gameBlocks.ts`; design in `docs/blocks-design.md`).** Layout and looks are plain HTML and CSS (the model already knows them); the logic is tags of ours (`x-state`, `x-scene`, `x-map`, `x-platformer`, `x-battle`, `x-dialog`, `x-timer`, `x-calc`, `x-list`, `x-rule`, `x-asset`/`x-art`; `game-*` are aliases) run by a runtime the page does not carry (`X_RUNTIME`, built by `node scripts/build-xblocks.js` from the block files; a test fails when it is out of date; `withEngine` adds it at show/test/save time). **State is the only bridge** between logic and page: numbers become CSS variables and `data-` attributes of `<body>`; effects (`gold+=1 say:"..." go:scene`) and tests (`hp<=0 && key`) are one small language read by one evaluator, no `eval`. `chooseGameWay` sends a platformer or a world game (`WORLD_WORDS`) here; arcade classics keep `Game.run`. **Exception to "a file is never cut into pieces written apart", decided for this kind of page only:** a page of blocks is declarative and every piece is a section that names what it uses, so `buildXPage` writes it in short sessions (outline, one drawing per object, base CSS, then each section's task list and each task), each seeing only the outline, the names defined so far (read from the page, never from a model), the page of the blocks it uses and the end of its own section; the page only grows at its end. After every task the fragment is REPLACED by the right form (`xMend`, `mendNames`: tags, effects, names), never only reported; a task whose problems remain is written once more with the exact problems; a task that comes back empty twice is left as a stub and the build goes on. Before any drawing a **style card** is made once from the game (`STYLE_CARD_INSTRUCTIONS`: outline width and colour, shapes, relief, palette, detail), kept in the page's `x-build` mark, and every drawer gets it plus the first finished drawing as a reference, so the drawings belong together; there is no limit on what is drawn (a pipe with a rim and a darker side matters), only text, numbers, buttons, panels and the HUD are never drawn (the look defines `.btn`, `.panel`, `.hud` once) and a section with no block (a menu, an end screen) is written in one piece. Objects are drawn apart by a drawer that sees one object (`x-asset` SVG, cleaned) and the main model only places them by name (`<x-art of="hero">`, or `art:hero` in a legend). A block that does not exist is asked about firmly three times before anything is made. **Any complex program is built by the general construction engine (`src/core/construct/`), which knows no genre.** Any new program goes through `buildProgram` (a model's yes/no questions decide that it is a program to make; the length of the request decides nothing): (1) requirements (a closed JSON form: numbered, atomic, testable statements), (2) **the state is written FIRST, then the plan is made in three small questions, one kind of unit each, so the kinds cannot be mixed up and every question sees the keys of the state** (before them, **`Structure`: the parts of the program as a core plus features, one line each (`STRUCTURE_INSTRUCTIONS`, the wording the prompt lab found steadiest on a 4B model, with a rule that a family of similar things is ONE feature holding a table); kept in `Plan.structure`, shown to the three questions ("cover every part"), NOT to the writers (shown to them it made units worse in the prompt lab: landOn 25 to 6, stepPlayer 37 to 18 on a 2B), it is context and not units; `structureLines` keeps only `core`/`feature` lines**; then **`Style`: one call, once, decides how the whole program looks (`STYLE_INSTRUCTIONS`: palette, size of a unit, how things are drawn, text, where the numbers go) and every layout and view is shown it at priority 88 (`Plan.style`, `styleLines`), so what different units draw belongs together; a view whose box holds elements (`innerIds`) is told to write those elements, and is faulted when it names none of them**; after the three questions, **`Wiring` (`wiring.ts`): one table says for every unit which keys of S it reads and writes and which functions it calls, plain checks read it with no model (a key written and read by nobody, a function called by nobody, a view that writes, a function that touches S, two handlers on one event, a unit with no line), one review call puts the faults right once, the calls become the unit's `uses` and its task says which keys it writes and only those**; then **`Shared`: the lead of the team decides what several things do the same way and writes it ONCE** as at most five functions that work on one thing of any kind (`moveThing`, `hits`), `none` when nothing is shared; the three questions see them and never write a per-kind version; they are written first, ONE call each (`shared` on the unit, `GROUP_MAX` = 1, examples run and checked like any function), and every unit written after them is shown their code whole, once, under "Shared functions" (`context.ts`); `Screen`: the views, each with the element it draws into; `Actions`: the handlers with their events, `tick 16` for what moves by itself; `Calculations`: the pure functions, always with arguments and examples), asked as lines of `kind name | what | requirements | extras`, of five kinds (`state`, `layout`, `fn` = pure function with a signature and examples, `view`, `handler` with its event), where `completePlan` keeps only what can exist (real unique names, a unit that serves no requirement is dropped, a state and a layout always exist, uses are resolved, circles broken, requirements with no unit are asked about once more), (3) a skeleton page assembled by code and running at once with stubs (`assemblePage`), (4) the units written in dependency order, small functions of one kind grouped in one call (`groupUnits`), each checked by code (it parses, it defines its name, a fn does not touch the page or S, a fn's examples are RUN in an isolated context with a time limit, `runExamples`, and every view, handler and fn is run ONCE ON THE REAL STATE with the page replaced by stand-ins, `smokeRun`: a name that does not exist or a key S does not hold fails there, as it would in the page) and corrected once with the exact failures; what code can put right is put right by code, never by asking again (a function written as a method gets its `function`, `bind.ts` gives `S.` to a key of the state used as a variable, `reconcileIds` takes the layout's id when the plan named the same element another way, `keepState` removes a parameter named S from a handler and turns `S = ...` into `Object.assign(S, ...)`, the assembly makes the element a view draws on with `getContext` a `<canvas>`, and `mend.ts` rewrites a name the model invented into the one that exists when ONE clearly stands for it: by spelling, by the words a name is made of (`timeLeft` / `time`) or by meaning in French and English (`temps` / `heure`, `vies` / `lives`, `width` / `w`), for free names, calls and fields of the state; two as likely or none near is left to the model, who is shown the names); `fixes.ts` also rewrites, with no model: typographic quotes, `import`/`export`, a cut-off ending (brackets closed), key names, only for the keys the program's own events name (`'Left'` becomes `'ArrowLeft'` only when the plan listens for `ArrowLeft`; a program that listens for something else is left alone: **a repair by code is always read from what THIS program has, never a rule laid over every program**), a function that changes its argument and returns nothing (it works on a copy and returns it, `pureCopy`), a call whose result is thrown away (`S.player = applyInput(S.player, ...)`, `keepResults`), arguments in the wrong order (`orderArgs`), an id the page does not have (`mendIds`), a top-level name two units declare (`renameCollisions`), `state` / `canvas` / `ctx` used without being declared (declared at the top of the function), and a mode word that means running (`running` for `playing`) or is the word the program sets spelled another way (`game_over` for `gameover`, `mendModes`); a view loses the wipe of the whole canvas and its calls to other views (`mendView`), `const S = window.S` is removed (`dropOwnState`), a tick handler that resets the flags the key handlers set loses that line (`keepKeyFlags`), a function that returns its changed copy counts as handing its argument back (`returnsFirstArg`), canvases no view draws into and repeated ids are left out of the layout (`provideIds`), a function planned as a drawing and examples that contradict each other are dropped (`completePlan`), a function that calls one not written yet is not judged on its examples until the page is played; a call whose answer is a piece of the state (an object made only of keys of S) keeps it with `Object.assign(S, f(...))` (`returnsStatePatch`, `keepPatches`), a function that returns a copy spread into an object counts as handing its argument back, a view that reads `S.canvas` gets `canvas` (`pageNames`), an example that does not parse or is written with `...` is dropped and a long call is no longer cut at 200 characters (`usable`); a view is shown only the element it draws into (never the HUD ids of the layout, which it then wrote into); the format example of the plan prompts is marked as being about another program and is NOT in the change prompt (a small model copied it into the game); when `Shared` gives five functions the `Calculations` question is skipped (it only repeated them); a shared function that takes the state, or more than three arguments, is dropped (`wholeProgramFn`: the first real build with the 4B gave `updateState(state, dt)` and `handleInput` as "shared", written first, and the views then carried the physics); a reply that holds one function under another name is that unit's function (`extractUnit`); a view that changes S while it draws, or that uses `ctx` on an element that is a box, is a fault; **What is global to the program is written once, by the page, never by a unit** (the loop, clearing the canvases, drawing every view, key listeners, S, `canvas` and `ctx` of a view, `PAGE_DOES` in `docs.ts` is in every instruction): a unit writes only what is specific to it, and when it writes page work anyway it is removed (`dropPageWork` unwraps a timer or frame loop and drops a key listener, `mendView`, `keepKeyFlags`); a handler that only sets a flag of the state is written by code with no call (`trivialHandler`); a unit that serves nearly every requirement is not shown the list, a view is told only of the functions it uses; a correction that returns the same code stops (`MAX_FIXES` = 2). **Repairs by a model are a last resort, never the way the code gets to work: when a fault appears again and again, the cause is in the plan or in what is shown to the writer, and that is where it is fixed.** every element of a repeated id is wired; timers and key listeners a view or a tick handler starts itself are named as faults; after play a number of S that is NaN or infinite is attributed to the tick handlers that write it; a planning question that comes back as an essay with no line is cut (`essay` in `build.ts`); handler events are `click #id`, `keydown NAME`, `keyup NAME`, `tick 16`, never a condition (collisions, wins, game over are checked inside the tick handler); one unit per call (`GROUP_MAX`: three together gave one function out of three); the state is shown with the fields of the items of its lists and the value of its modes; a function is run with frozen arguments (changing one, or returning nothing, is a fault) and may not call a view or a handler; every canvas is cleared by the page before the views draw; elements a view or an event needs are added to the layout by code (`provideIds`); and before any browser test the page is PLAYED in an isolated context (`playPage`: loaded, drawn, keys pressed, 200 ticks), each error is attributed to the function it came from and that unit is written again once; every unit is also READ against the state (`stateUse.ts`: a field read on an item that does not hold it, a key of S that does not exist, a mode compared with a word nothing sets, a handler with no effect at all; a read under a test is the program's own business) and a function that runs and answers with the kind of the examples' is kept after one correction. **Each unit is checked the moment its call ends and, while something is wrong, goes back to the model with the exact fault to be written again (up to three rounds, stopping when an answer is worse); the checks include what the unit is SEEN to do on the real state (`smokeRun`: a view that touches nothing of the page drew nothing, a tick handler that leaves S as it was in 30 ticks and a key handler that changes nothing do nothing), and each kind of unit is given STRICT RULES (`STRICT_RULES` in `docs.ts`, one line per fault small models made again and again) in the first write and in the correction.** **The checks only stop code that cannot work, never an idea: the writers are told to be as original as the request allows**; every writer sees the state two levels deep, the elements of the page with their tag, and the signature of every function (`Functions you can call`); (5) the page assembled again after every unit, so the preview fills in, and (6) **scenario tests** (`scenarios.ts`): one call turns the requirements and the ids of the page into scenes (`click #start ; press ArrowRight 8 times | #player moves right`, `press Escape | #menu shows`) kept in the page's construct mark; the test run plays each in a fresh load and judges in code by measuring the element the scene is about. A scene only says what MUST happen, never what must not (an enemy moving too is never a fault); a failed scene becomes a change request on the engine page; a runtime error of the page is attributed to the units that use the name it names and each gets its own error (never a list of every function). The plan, the gaps and a change are asked as lines (`kind name | what it does | requirements | uses, on, into`), not as JSON; the engine's sessions do not think (`stageEffort`); "Copy full log" lists every call to a model. The two parts that set the quality of the rest: **the task list** (`tasklist.ts`) and **the context engine** (`context.ts`): every writer is shown only the requirements its unit serves, its own task, the CONTRACT of what it uses (signature and one line, read from the code that was accepted, and the code itself only when short and verified), the shape of the state and the ids of the page, and the names that exist; never a reply that failed, never another unit's code, never the plan; sections have priorities and the lowest go whole when the room is short; each call leaves a trace of what it saw in the log. A page this engine made keeps its plan in an `x-construct` comment and each unit between `/* unit:name */` marks, so a stopped build is taken up again by "continue"; skip and go-back work on a unit. **The platformer made from two closed forms is shelved in `src/core/shelved/` (nothing imports it, tested alone in `tests/shelved/`): it was a genre shortcut that could make the engine look better than it is; do not wire it back as the way games are built.** The older block sessions (`buildXPage`, `editXPage`) remain only for pages of blocks that already exist. Code files of any other kind keep the rule: never cut apart.
- **Slide quality rests on the source text and on rules, not on the small model's flair (`deckFacts.ts`, `look.ts`, `themeGen.ts`, `color.ts`).** The facts of a given text are read without a model: its parts, figures, dated events, a rise from one value to another (`partFor`, `figuresIn`, `eventsIn`, `trendTable`); `enrichPlan` gives a part full of figures the Stats layout, a run of dates the Timeline, a rise its Chart (numbers are the text's own, never invented); each content slide gets a one-line takeaway or insight (`takeawayOf`, `insightOf`); a slide the model leaves empty is written from the text (`slideFromPart`); nothing is ever cut with "…" (`clipPhrase`). Slides have named templates (`Layout:` cover, section, agenda, quote, bignumber, compare, closing; agenda and section are made by the app, no model call). **Themes are made, not listed:** a hue, a mood and a style (`generateTheme`) give hundreds of looks; `findTheme` reads words in French or English ("vieux", "technologie", "pour la classe") and `Theme: <words>` works in the deck text; `Theme: id | accent=.. bg=.. titlefont=.. deco=.. cover=.. pattern=.. bgkind=.. seed=..` changes the theme for EVERY slide, `Style:` for one slide. **The model decides the look as JSON** (`LOOK_SCHEMA`, step "Look" in `makeDeck`: 2 to 4 colours, two fonts, a procedural background kind and seed, optional looks for single slides), checked by `lookProblems`, asked again once, then `normalizeLook` drops what is invalid. **Readability rules always apply** (`legalize`: text and titles 4.5, accents and muted 3, text on panels 4.5), whatever the model or the person asked for, and backgrounds are weak on content slides (`backgroundPrims(kind, seed, theme, strength)`: gradient, mesh, waves, rings, dots, stripes, grid, confetti, blocks; the same seed gives the same picture, another seed another one). Fonts: a title font mixed with a plain body font per theme, all on a standard Windows. No outside palette data is shipped (the npm palette sets come from sources with unclear licences).
- **A presentation request is understood by simple questions, not only by words (`src/core/deckBrief.ts`, `fuzzy.ts`).** The word lists only know how their author talks, so `makeDeck` first asks the model short closed questions one after the other (number of slides when the words found none, where it is shown, which style, which colour the subject calls to mind, and the facts the person's OWN text states, listed one by one and kept only when really in the text, `askFacts` / `groundedFacts`; the colour is the model's own pick, no examples in the question). Each answer is a choice of a list, checked with `snap` (a few letters off still counts) and a failed question leaves the default. The look the person named in words still wins (`findTheme`, which now puts typing slips right with `mendWords`); otherwise style and colour make a theme (`themeFromBrief`). **Research follows the facts, not the length of the text:** the count of facts against `FACTS_PER_SLIDE` per content slide (`infoLevel`): `enough` = no search; `some` = one search for the plan; `none` = that search and one per content slide (`DeckOptions.search`, sources renumbered so every slide's `[n]` is unique, all listed on the sources slide); with web search off the closing message says the facts come from memory. A new way of speaking must be handled by these questions, never by adding words to a list.

- **Word, Excel, websites and calculators are made from templates (`src/core/templates/`: `kit.ts`, `word.ts`, `excel.ts`, `site.ts`, `build.ts`, `index.ts`).** A new file that the person names (Word/docx, Excel/xlsx, a landing page or website, a simulator/converter/calculator page) goes through `makeFromTemplate` before the usual file steps: the template is chosen by the words (the longest match wins), else by the model from the list, and the small router can send an unusual need to the free way (`askRouter`); the model fills a CLOSED JSON schema (constrained like the game description) in the language of the request, the app checks it (`problems`), asks again once, and renders the text form that becomes the real file; anything that fails falls back to the usual writing (and clears what was shown). 28 Word templates (the fixed words come from `kit.ts` in six languages, a block with no data is left out, `extra` adds parts), 26 Excel templates (formulas already in place and checked with the app's own evaluator in `tests/templates.test.ts`; the model gives rows, settings and the HEADERS in the request's language; `extra_columns`, `blank_rows`), one calculator template (formulas run only after `safeFormula`) and **websites made from blocks (`src/core/page/`)**: `catalog.ts` describes the 17 blocks ONCE (the JSON schema the model writes, the fields of the visual editor, `toPuckData`/`fromPuckData`), `blocks.tsx` draws them as React components (page preview, static export and the editor all use them), `theme.ts` reuses the slide theme engine (readable colours guaranteed) with a procedural hero background, `html.ts` makes the page (`pageToHtml`, one file) or the files of a site (`pageToFiles`: index.html, style.css, script.js, `vendor/` for the libraries it uses, `licenses.txt`, `page.json`); the description stays inside the HTML (`#site-spec`, `pageSpecOf`). **Libraries (all MIT/ISC), copied into `vendor.generated.ts` / `icons.generated.ts` by `scripts/vendor-anim.js` and `scripts/vendor-icons.js` so there is no network and no node_modules at run time: Puck (`@measured/puck`, the visual block editor, opened by "Edit blocks" in the artifact panel, lazy loaded in `PageEditor.tsx`), AOS (scroll reveals, from each block's `animate`), animate.css (hero entrance, a subset), countUp.js (figures that count), Lucide (349 line icons, the default; `icon_style` icons/emoji/none; a name or a meaning like "secure" finds the icon).** Only the libraries a page uses are put in it; nothing moves under `prefers-reduced-motion` or when `motion` is none. tsParticles was tried and drew nothing even in a plain page, so the particles hero effect is a small canvas of our own; typed.js is GPL, so the typewriter is our own too. Save as for such a page offers one html file, a zip of the site, or the description. **A site of several pages (`src/core/templates/multipage.ts`, branch of `makeFromTemplate`):** asked by the words (`wantsSeveralPages`: multi-page, plusieurs pages, an about page and a contact page...), never a reason to leave the blocks. The model works in small runs: one for the plan of the site (look, files, what each page is for, `SITE_PLAN_SCHEMA`), then one per page that sees only the plan and its own page; the look (theme, accent, background, radius, spacing, seed) comes from the plan and the first page so every file carries the same CSS text, the menu (`nav`, `current` of `PageSpec`) goes from page to page, and a link that names a page becomes its file (`fixHref`). Each file is an artifact (index.html, about.html...); the preview moves between them. When the plan or a page is refused twice, a single page is made. **No outside collection of document templates is shipped:** those found (LibreOffice community templates, JSON Resume themes, pptxgenjs, docxtemplater) are mixed-licence or need real .docx/.pptx files to start from. The document appears while the model fills it in**: the partial JSON is repaired (`repairJson`) and drawn every ~180 ms with `render(data, {live: true})`, which draws only what exists (no empty rows or sheets waiting), so it grows piece by piece and the empty template is never shown; the schema puts the headers first, then settings, then rows. No outside template collection is shipped: those found (LibreOffice community templates, Flowbite/DaisyUI/HyperUI components, JSON Resume themes, pptxgenjs, docxtemplater) are mixed-licence, need Tailwind or a network, or need real .docx/.pptx files to start from.
- **Versions of every file (`src/core/versions.ts`, `versionBook.ts`; `VersionMenu.tsx`, `VersionsPanel.tsx`; saved in `artifact-versions.json`).** A file is the same file across turns (`lineageKey`: chat + title), and the Artifacts page lists it once (`currentFiles`); its earlier states are its versions. **Nothing is deleted unless the person does it** (`removeVersion`, only from the versions page, never the one in use; numbers are never reused). A version is made only when the saved text differs from the one in use (v1 = base, v2 = first change...), titled by the request that caused it (`note`), "Edited by you" for hand edits. **Nothing is saved while an answer is being written or improved** (`Chat.tsx` saves on `done` only): v1 is the finished file, then one version per change the person asks for, never one per redraw or kept fix. **Stored as differences** (lines, with a full copy every `CHECKPOINT_EVERY` versions or when a delta is not smaller). **Going back never erases:** "Go back to it" adds a new version branching from the old one (`restore`); "Use as main" only moves the pointer (the app, the chat's file text and exports use it) and the next change branches from it and replaces it. Chat panel: a drop-down on the file's head to look at any version read-only, with a button to the Artifacts page (versions list, any two compared line by line, rename, delete). Files saved before this get their versions from their old states at start (`seed`). Deleting a file deletes all its versions.

- **The prompt lab (Developer settings, `src/core/promptLab.ts`, `labRunner.ts`, `PromptLab.tsx`, `promptLabPlans.ts`; guide in `docs/prompt-lab.md`).** A Markdown file of prompts, each with its ideal answer at the end of its section (`### Ideal`, optional `### Checks` and `### Options`, options also in a front matter), is asked as written (no planner, no router, no construction engine, `maxContinues: 0`) of the installed GenieX models picked, one loaded at a time, `runs` times each; every answer is scored by code against the ideal (words, form of the `|` lines, length; 60 % with 40 % checks) and the best run of each prompt and model is shown, with the report as Markdown. It exists because a request for a game in the chat always starts the engine. When the format or the scoring changes, change `docs/prompt-lab.md` and `LAB_EXAMPLE`; the tests read both the example and the ready planning series (`promptLabPlans.ts` round 1, `promptLabPlans2.ts` round 2, `promptLabPlans3.ts` last round, `promptLabUnits.ts` the writers unit by unit, `promptLabUnits2.ts` the same unit asked in ten ways for five programs of different kinds (190 prompts, `docs/prompt-lab-units-2.md`: load it with the file import, no button; a first run on a 2B showed that the engine's own instructions are what makes a state or a layout come out right and that a plain sentence or a telegraphic note is always worse, so `docs/prompt-lab-units-quick.md` keeps the engine's instructions and varies only the context: 60 prompts, about half an hour on a 4B), copies in `docs/prompt-lab-planning*.md`). **Code checks** (`labCode.ts`): `given: code`, `loads` and `run: expression => expected` run the answer's code in an isolated context (fresh for every check), so a prompt that asks for a unit is scored on whether the code WORKS; `promptLabUnits.ts` builds the prompts of the units of a small platformer with the engine's own `ContextEngine` and `WRITE_INSTRUCTIONS` (the real input of a writer), with working ideals that the test runs against their own checks. Round 1 result on a 4B model: "a core plus features" was the form it followed best and the only one whose score did not fall with a much bigger request; the scores reward looking like the ideal, so a prompt that hands the model its own list (C2) scores high without planning anything. Round 2 result: the core first with placeholders and one example of the form (B2) was the steadiest (4B 83.5, 2B 80.4, and the only one whose average held); features-first broke the 2B; a 3B coder model scored high only on its best run (average 35-57), so best-of hides it; on the big request the models made one feature per kind of enemy and per level, which the last round answers with a family rule. Last round: the family rule helped the 4B a little (83.2 best, 77 average, against 74.5) and the 2B did not follow it; a limit on line length changed nothing; the 4B failed on the last two prompts with a server error (terminated, fetch failed), not with a bad answer. The result is `Structure` in the engine. Unit writers (code run): the 2B is not usable to write units (mean 45.6, free names like `distance`, `platforms`); the 4B (70.3) writes small units well (onJump 90, drawHud, collectCoins, a view that passed 7 of 7 runs) and fails where the logic is subtle (`landOn`) or where one unit does too much (`onTick`: 5 of 12; wrong time step, no gravity, a list put in a list), so a big handler must be split by the plan, not repaired. A fence written with look-alike marks is read as a fence (`likeFences`). A prompt with `run` checks is scored 80 % on them. Short round on the 4B (60 prompts): the engine's context as it is (W1) is the best way to ask (64.4), a checklist after it equals it (62.7), the parts of the program cost 7 points (57.6), the task alone 56, the task and the state alone 54: the full context (requirements, task, state, elements, functions) is what the 4B needs, so nothing is removed from it. A view that wrote `document.getElementById` was judged too hard by the lab and the check was loosened; `S.<its element>` in a view becomes `canvas` (`pageNames`).

- **Voice (dictation and voice chat)** (`src/renderer/voiceChat.ts`, `src/core/live.ts`, `endpoint.ts`, `transcript.ts`, `VoiceSetup.tsx`): the words appear while they are said (the audio so far is decoded again, previews are skipped when the recognizer is busy so they never delay the final decode, and a preview that saw all the speech IS the final text); the silence that ends an utterance follows what was said (short after a finished sentence, longer after a comma or a linking word); a minimum level and a minimum speech length are settings (Settings > Voice > Microphone, with a level test); what a recognizer invents on silence ("Thanks for watching") is dropped. Using the mic or the voice chat without the models opens a one-click install card, never the settings. Foundry Local speech models (`foundrySpeechModels`, ids `foundry-stt:<alias>`) are dictation models run through its `/v1/audio/transcriptions` and are the recommended one when it has an NPU build (the voice worker's sherpa-onnx has no NPU); written from its documentation, not tried against a real install; when it fails the CPU model takes over if installed. Voice chat has its own model (`voiceModelId`: "" = Qwen3.5-2B when installed (the GenieX build first: Foundry Local refuses repetition penalties; Qwen3-1.7B and Phi-4-mini repeat themselves a lot and are left out), else the best other small model measured wholly on the NPU, `fastVoiceModel` in `src/core/voicePick.ts`; "chat" = the conversation's model; or an id), when the voice chat button is used with a model missing, one card installs the whole voice pack in one click (speech model, read-aloud voice, and Qwen3.5-2B alone, never the whole Dynamic pack), may draw charts and (only when the Pictures tool is on, off by default) show Wikimedia pictures, which appear on the voice screen and are never read aloud, the voice saying in a sentence what they show, the voice bubble opening into a frame around them, and to spare the voice context (`src/core/visuals.ts`): the chart and picture instructions are given only when the request asks for one (`visualNeeds`), older charts and pictures in the history become one-line notes (`compactVisuals`, only the latest is kept whole so it can be changed), and a note copied by the model is never read aloud, tells the model it is a voice conversation (transcription errors, read aloud, may be cut in on), waits `waitMs` (2.5 s by default, a little less after a finished sentence, more after an open one) before answering, and the person cuts in only by saying real words (`speechWords`: not a cough, a laugh, a hesitation or the assistant's own voice) without a break for `interruptMs` (1 s) above `interruptLevel` (45 % of the meter): until the words are confirmed the voice is only held (`Player.pause`) and goes on from the same word if the final transcription is empty; the words of the answer appear under the orb as the voice reaches them (`caption`, `spokenPrefix`); the spoken text is held back while markdown is still being written (`settledSpeech`, never skipped) and long sentences are cut at a comma; the voice screen is the chat itself (no full-screen orb): the answer's words are grey until the voice reaches them (`VoiceReading`), and the input bar becomes a listening bar that glows with the sound (`VoiceBar`) with the microphone picker (`micDeviceId`, switched live) and a Models panel to change hearing, thinking and voice on the spot, installing a model not there yet when chosen; the automatic voice model (`voiceModelId` "") is always Qwen3.5-2B or 4B, whichever is nearer in size to the chat model (`voiceModelNear`, a Dynamic pack counts as its biggest model), and a model chosen by hand is kept; the default read-aloud voice is Kokoro at full quality (the int8 one muffles the sound and stays as a light choice); the voice is given another text than the screen shows (`forVoice` in `src/core/speakNumbers.ts`: numbers, years, percentages and money written out in the answer's language, Vietnamese and other foreign letters reduced to the alphabet of the voice; an English voice silently drops digits and letters it does not know, which was the "skipped words"), the answer is cut for the voice at safe points of the written text (`SpeechStream`, never by comparing two cleaned versions) and the reading progress of each sentence is kept between sentences (`Player` keeps its log); acronyms are said as the words they stand for (a short list, and the ones the answer defines itself, `learnAcronyms`) or spelled letter by letter, signs and units are written out (`speakSymbols`), none of which changes what the screen shows (`toSpeechText` only removes markup, because the screen reads from it too); a sentence with no sound counts as said at once (`spokenPrefix`), a paused voice is not restarted by a sentence arriving (`Player.held`), voice models load one at a time (`ensureVoice`); the speech runtime (sherpa-onnx) has no NPU support: asking for NPU puts the setting back on CPU, only Foundry Local speech models run on the NPU; and when the person cuts in the whole answer is kept (the screen shows what was heard in full colour, the rest grey, `heardWords`) and the model is given all of it with `INTERRUPT_MARK` placed where the voice had reached (`markInterruption`), so "pick up where you left off" resumes from there.
- **A full window is handled, never a silent stop** (`src/core/compaction.ts`, `memo.ts`, `context.ts`, `streamComplete` in `chat.ts`; "Compact" button in the context menu of `Chat.tsx`). The oldest part of a chat is summarized by the model from 65 % of the room (`COMPACT_AT`), before anything is cut, and kept with the conversation (`Conversation.memo`, checked against its turns by a hash of the last covered one). **The summary is written in parts**: each stretch of messages gets its own part, parts are never rewritten, and only when they outgrow 20 % of the window are the two OLDEST merged (recent stays detailed). Files written in the folded part travel with the summary in their newest version. A request that still has to be cut in a hurry gets a recap made without a model (`digestOf`), never a bare "left out". A server that refuses a request as too long gets it again, shorter (`isContextOverflow`). A cut-off answer is continued with a window on its END (`windowAnswer`: the names it defines, then its last lines), not the whole text; the app tells a full window from the answer limit, folds the older chat once in the first case, and keeps going while an unfinished file grows (`maxContinues` x 4), stopping when two rounds add nothing, with a message that says why.

## What is known about the NPU here

Read `docs/npu-load-research.md` before touching model loading. In short: GenieX 0.9.3 starts `geniex serve --compute npu` with the whole model on one NPU session (about 3.5 GB of addresses); a refused buffer is `1024 x vocabulary x 4 bytes + 4096` (the logits for `n_ubatch` 1024); a failed load can leave the NPU unusable until it is reset or Windows restarts; the NPU works in the PC's RAM, so a full RAM makes every load fail. `GGML_HEXAGON_MBUF` and `GGML_HEXAGON_DEVICES` are not read by this GenieX. The NPU load test and the benchmark in Developer settings try settings from the least to the most limiting (`src/core/npuLoad.ts`).
