# Open NPU: notes for Claude

Windows on Snapdragon (ARM64) desktop app: Electron main process in `src/main`, React renderer in `src/renderer`, logic shared by both in `src/core`, tests in `tests`. The user writes in French; answer in French.

## Rules that were broken before. Do not break them again.

1. **Hooks go above every early `return` of a component.** A `useState`, `useEffect`, `useMemo`, `useRef`... placed after `if (!x) return ...` makes React throw error #310 ("Rendered more hooks than during the previous render") and the window shows "Open NPU hit a problem drawing the window". It happened in `Chat.tsx`, which returns early when no model is selected, and it happened more than once. `tests/hooks.test.ts` reads every renderer component and fails on a hook after an early return: run it. When adding state to a component, read the whole function first and put the hook with the other hooks, at the top.
2. **Pull requests target `main`, never another `claude/...` branch.** Work merged into an intermediate branch never reached `main` before. When creating a PR, check the base. Before saying something is done, check that it is in `main`.
3. **Before pushing:** `npm ci` (if `node_modules` is missing), `npx tsc --noEmit -p tsconfig.main.json`, `npx tsc --noEmit -p tsconfig.renderer.json`, `npx vitest run`. All must pass. A push to `main` builds the Windows installer in CI (`.github/workflows/release.yml`) and publishes `Open-NPU-Setup.exe` on the `latest` release; that build runs the tests on Windows, where timing-based tests can differ. `git pull --no-rebase` first: other sessions push to `main` too.
4. **No model name or tool name in commit messages or code comments.** Commits end with the attribution lines given by the session.

## What the user wants (decided, do not reopen)

- Models should run **on the NPU**. Badges on every model: NPU (best), Hybrid (part on the CPU), CPU (worst). Hybrid and CPU are never chosen silently: they are a last resort the user allows (`allowHybridLoad`), and the badge says it.
- A model the app does not know (not in the catalog, not in a Dynamic pack) is **checked once after it is installed**: loaded under the best setting this PC accepts, NPU first, then badged. Only loading is checked, never the quality: how good a model is stays the user's call.
- When the app sees the NPU is stuck it **resets it by itself** (scheduled task created once with one Windows permission, then no prompt). Do not make the user press a button or restart the PC.
- The benchmark has a **Launch check** mode (does each model load and answer, no quality tests) and Developer settings has a page that compares GenieX with Microsoft Foundry Local on the same models (`src/core/foundry.ts`, `src/renderer/EngineCompare.tsx`). The Foundry Local side is written from its documentation, not tried against a real install.
- **Building files (`src/core/build.ts`):** a small program (game, tool) is ONE page, written whole by one session, with no planner call for a plain request. A file is never cut into pieces written apart: a file too long for the window is continued by the same session. The contract shared between files is read from the code, not from a model, and checked (a page's own script must parse and find its elements). The user sees which file is being worked on, its code and preview live, and a line saying what happens now: every file shows its stages (starting point, rules, write, check, fix) as chips with their time, and the finished page gets a visible test run (it is run, its keys and buttons pressed, a screenshot shown) with a fix and a second run when it shows a problem; a fix that makes it worse is undone. A usual program (snake, to-do, calculator, tic-tac-toe, stopwatch, quiz) starts from a tested page in `src/core/skeletons.ts`; any other program gets short written rules first. Helper sessions that mend a file think (medium effort), those that write do not. In the browser preview (`npm run dev:renderer`) a message with "snake" plays this whole pipeline with a pretend model. Speak as one assistant ("I", never "we"): the files are the assistant's own work, never "the code you gave me".
- **Foundry Local models are part of the app** (Models, "Microsoft Foundry Local", `foundryCatalogEntries` in `src/core/foundry.ts`): listed from `foundry model list` (which does not start its daemon), installed with `foundry model download`, run through its server for the chat, badged NPU / Hybrid / GPU / CPU by the hardware of their build until measured, and the person can mark any of them differently (`setRunsOn`). They are not in `allEntries()` on purpose (that list is what the benchmark tests with GenieX); look a model up with `entryById`.
- **The Dynamic model uses the best build whatever the engine.** The app is called Open NPU: when Foundry Local has a build of a pack model made for the NPU that measured faster, the pack runs that one (`foundry` on the model in `dynamic-data.json`, installed with Foundry Local, which is installed too for a model only it has, `foundryOnly`); the GenieX file is the way out when Foundry Local is not there or fails. Starting a server is never a reason to keep a slower build. When two engines were tested on the same model, the faster one is shown and used: the quality of a short test varies, so it does not decide.
- **One engine and no leftovers.** Whatever starts a model first closes the servers that are not this app's (`closeStrayServers`: a geniex whose parent is not this app, Foundry's daemon when no Foundry model is in use) before the heavy NPU reset. The app's own server and its conversations are left alone. Foundry's daemon is stopped after each Foundry model: it keeps RAM, and the NPU works in RAM.
- **Foundry Local facts measured here:** its NPU builds size the attention cache on prompt + `max_tokens` and run the prompt in blocks of 64, so a small `max_tokens` (12, 16) kills its daemon (`GroupQueryAttention` errors): ask for at least 256. Its server refuses non-zero penalties (`presence_penalty`): a request refused for an optional field is sent again without it (`streamChat`). The model is asked by the build id it announces when loaded, not by its alias.
- **The Dynamic model has a router** (`src/core/router.ts`, `RouterPanel.tsx`): a tiny model (Qwen3-0.6B, about 0.4 GB) that reads the requests the words are unsure about and names their kind in one word, a second or so. It runs on the PROCESSOR, in a second `geniex serve --compute cpu` on port 18182 (`routerSrv` in `main.ts`), never on the NPU (which holds one model, and swapping it for every request would cost more than the answer). This is decided: the user wanted a "System 1" model and said to build it, so the rule against silent CPU use does not apply to it. It needs no training (the kinds and examples are in its prompt), has a short timeout and always falls back to the words' guess, and is installed from the Dynamic settings. Its answer is shown in the chat ("sorted by the router").
- **Recommended means fully on the NPU, from any provider.** The Recommended list and Dynamic never use a model known to run hybrid, on the GPU or on the CPU (`recommendedModels`, `onNpuOnly` in `main.ts`); when a model exists on two engines, the full-NPU build is the one shown, then the faster. Foundry Local is one provider among others (GenieX GGUF, native bundles), never the criterion. Dynamic falls back to a non-NPU model only when nothing else of the pack is installed.
- **The router belongs to the packs** (`router` of each pack in `dynamic-data.json`, outside `models` so it is never picked to answer): installing or removing a pack installs or removes it (`packParts`).
- **Tested models are written in the app** (`src/core/tested.ts` for the list, `scores.json` for speed, quality, where they ran and, when it was not the usual one, the load setting they needed): they are listed with their measures installed or not (Foundry Local ones too, when Foundry Local is not there; installing one installs it first), and the ones that did not run fully on the NPU sit in the folded "Not fully on the NPU" section, never recommended. A new benchmark result is added to these two files.
- Logs must give the real reason of a failure (server lines, the buffer that was refused, the RAM) and have a "Copy full log" button.

- **Voice (dictation and voice chat)** (`src/renderer/voiceChat.ts`, `src/core/live.ts`, `endpoint.ts`, `transcript.ts`, `VoiceSetup.tsx`): the words appear while they are said (the audio so far is decoded again, previews are skipped when the recognizer is busy so they never delay the final decode, and a preview that saw all the speech IS the final text); the silence that ends an utterance follows what was said (short after a finished sentence, longer after a comma or a linking word); a minimum level and a minimum speech length are settings (Settings > Voice > Microphone, with a level test); what a recognizer invents on silence ("Thanks for watching") is dropped. Using the mic or the voice chat without the models opens a one-click install card, never the settings. Foundry Local speech models (`foundrySpeechModels`, ids `foundry-stt:<alias>`) are dictation models run through its `/v1/audio/transcriptions` and are the recommended one when it has an NPU build (the voice worker's sherpa-onnx has no NPU); written from its documentation, not tried against a real install; when it fails the CPU model takes over if installed. Voice chat has its own model (`voiceModelId`: "" = Qwen3.5-2B when installed (the GenieX build first: Foundry Local refuses repetition penalties; Qwen3-1.7B and Phi-4-mini repeat themselves a lot and are left out), else the best other small model measured wholly on the NPU, `fastVoiceModel` in `src/core/voicePick.ts`; "chat" = the conversation's model; or an id), tells the model it is a voice conversation (transcription errors, read aloud, may be cut in on), waits `waitMs` (2.5 s by default, a little less after a finished sentence, more after an open one) before answering, and when the person cuts in the answer is kept only as far as it was said aloud (`spokenPrefix`), marked `interrupted`, with a note for the model.

## What is known about the NPU here

Read `docs/npu-load-research.md` before touching model loading. In short: GenieX 0.9.3 starts `geniex serve --compute npu` with the whole model on one NPU session (about 3.5 GB of addresses); a refused buffer is `1024 x vocabulary x 4 bytes + 4096` (the logits for `n_ubatch` 1024); a failed load can leave the NPU unusable until it is reset or Windows restarts; the NPU works in the PC's RAM, so a full RAM makes every load fail. `GGML_HEXAGON_MBUF` and `GGML_HEXAGON_DEVICES` are not read by this GenieX. The NPU load test and the benchmark in Developer settings try settings from the least to the most limiting (`src/core/npuLoad.ts`).
